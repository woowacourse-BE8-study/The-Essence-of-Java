### 1. 메서드 호출의 차이: Call Stack의 관점

---

자바에서 메서드가 호출되면 메모리의 **Stack** 영역에 해당 메서드를 위한 공간(Stack Frame)이 생성된다.

- **`run()`을 직접 호출할 때**: 이는 일반적인 객체의 메서드 호출과 다를 바 없다. 새로운 쓰레드가 생성되지 않고, 현재 `run()`을 호출한 쓰레드(보통 `main` 쓰레드)의 콜 스택 위에
  `run()` 메서드가 올라간다. 즉, 싱글 쓰레드로 동작하며 비즈니스 로직만 수행될 뿐이다.
- **`start()`를 호출할 때**: `start()` 메서드는 내부적으로 새로운 콜 스택(Call Stack)을 생성한다. 그리고 그 새로운 스택의 가장 첫 번째 공간에 `run()`을 올린다. 이후 OS의
  스케줄러에 의해 해당 쓰레드가 차례를 얻으면 독립적으로 `run()`이 실행된다.

### 2. `start()`의 내부 동작 로직

---

`Thread` 클래스의 소스 코드를 살펴보면 `start()` 메서드가 단순히 `run()`을 호출하는 구조가 아님을 알 수 있다. 대략적인 과정은 다음과 같다.

1. **쓰레드 상태 확인**: 쓰레드는 한 번만 실행될 수 있다. 만약 이미 실행되었거나 종료된 쓰레드에서 다시 `start()`를 호출하면 `IllegalThreadStateException`이 발생한다.
2. **쓰레드 그룹 추가**: 해당 쓰레드를 관리하는 쓰레드 그룹에 등록하고 실행 준비를 마친다.
3. **Native 메서드 `start0()` 호출**: `start()`는 자바 코드로 작성되어 있지만, 실제 쓰레드를 만드는 작업은 자바만으로는 불가능하다. 따라서 OS의 시스템 콜을 호출할 수 있는 네이티브
   메서드인 `start0()`를 호출한다.

### 3. Native 메서드 `start0()`와 JVM의 역할

---

자바는 플랫폼 독립적인 언어이지만, 실제 물리적인 쓰레드를 생성하고 관리하는 권한은 운영체제(OS)에 있다.

- **JVM의 중계**: `start0()`가 호출되면 JVM은 해당 OS(Windows, Linux 등)의 API를 사용하여 커널 수준의 쓰레드(Kernel Thread) 생성을 요청한다.
- **리소스 할당**: OS는 새로운 쓰레드를 위한 독자적인 프로그램 카운터(PC Register)와 스택 공간을 할당한다.
- **Callback Mechanism**: 새로운 쓰레드가 생성되고 실행될 준비가 완료되면, JVM은 이 쓰레드를 자바의 `Thread` 객체와 연결한다. 이때 OS가 새로 생성된 쓰레드의 제어권을 갖게 되며,
  그 쓰레드의 첫 실행 지점으로 자바에서 정의한 `run()` 메서드를 호출하게 된다.

> **요약**: `start()`는 "새로운 스택을 만들고 쓰레드를 준비시켜라"라는 명령이고, `run()`은 그 스택 안에서 "실행할 내용" 그 자체다.
>

### 4. 왜 이런 구조로 설계되었을까?

---

만약 `start()` 과정 없이 바로 `run()`이 다른 쓰레드에서 실행되게 만들었다면, 개발자는 OS 수준의 쓰레드 생명주기를 직접 관리해야 했을 것이다. 자바는 이를 `Thread` 클래스의 `start()`
메서드 안에 캡슐화하여, 개발자가 '무엇을 할지(run)'에만 집중하고 '어떻게 쓰레드를 만들고 실행할지(start)'에 대한 복잡한 과정은 JVM이 대신 처리하도록 설계했다.

따라서 `start()`를 호출하는 것은 단순히 메서드 실행을 의미하는 것이 아니라, **하나의 독립적인 실행 흐름(Process 내의 Thread)을 탄생시키는 과정**이라고 이해해야 한다.

### 5. 핵심 정리

---

- **`run()` 직접 호출**: 현재 쓰레드의 콜 스택에서 단순 메서드 실행 (새로운 실행 흐름 없음).
- **`start()` 호출**:
    1. 내부적으로 `start0()` (Native Method) 호출.
    2. JVM이 OS에 쓰레드 생성 요청.
    3. OS가 새로운 콜 스택 생성 및 리소스 할당.
    4. 새로 만들어진 쓰레드에서 `run()`을 첫 번째로 실행.
