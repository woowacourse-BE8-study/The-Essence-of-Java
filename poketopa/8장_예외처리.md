# 8장. 예외 처리 (Exception Handling)

> `try-catch` 문법을 안다고 끝이 아닙니다. **언제 / 어떻게 / 무엇을** 던지고 잡을지가 실력의 척도입니다.
> 빅테크에서 가장 자주 보는 anti-pattern 들과 정공법을 함께 정리합니다.

---

## 1. Exception 계층 한눈에 보기

```
Throwable
├─ Error              (시스템 오류 - 잡지 말 것)
│   ├─ OutOfMemoryError
│   └─ StackOverflowError
└─ Exception
    ├─ IOException, SQLException ...   (Checked Exception)
    └─ RuntimeException                 (Unchecked Exception)
        ├─ NullPointerException
        ├─ IllegalArgumentException
        └─ IllegalStateException ...
```

| 구분 | 처리 강제 여부 | 의미 |
| --- | --- | --- |
| **Error** | X | JVM 단의 회복 불가능한 오류. 잡지 말 것 |
| **Checked Exception** | O (`try` 또는 `throws` 강제) | 호출자가 *반드시* 대비해야 함 |
| **Unchecked (RuntimeException)** | X | 프로그래밍 실수 / 비즈니스 조건 위반 |

## 2. Anti-Pattern ①: `catch` 안에서 재귀 호출하는 retry

```java
// ❌ Anti-Pattern : Exception 을 Error 로 만드는 위험한 방식
public void fetchData() {
    try {
        // 네트워크 요청
    } catch (Exception e) {
        fetchData(); // ⚠️ 무한 재귀 → StackOverflowError
    }
}
```

### 무엇이 문제인가?

- 종료 조건이 없음 → **무한 재귀** → `StackOverflowError` 로 프로세스 다운.
- 재시도 간격이 0초 → 실패한 서버를 *즉시* 다시 때림 → **Self-Inflicted DDoS** 유발.

### ✅ 올바른 Retry 패턴

```java
public void fetchData() {
    final int maxRetry = 3;
    for (int i = 0; i < maxRetry; i++) {
        try {
            // 네트워크 요청
            return;
        } catch (TransientException e) {        // ✅ 재시도 가능한 예외만 잡기
            if (i == maxRetry - 1) throw e;     // 마지막이면 포기하고 위로 던짐
            waitForNextRetry(i);                // exponential backoff + jitter
        }
    }
}
```

> **Spring 에서는** `@Retryable` (spring-retry) 또는 Resilience4j 의 `Retry` 컴포넌트로 같은 동작을 *선언적으로* 구현할 수 있습니다.

## 3. 재시도 전략: Self-Inflicted DDoS 를 피하는 3가지 무기

장애가 나면 클라이언트가 *동시에* 재시도해 서버를 더 망가뜨리는 현상을 **Self-Inflicted DDoS** 라 합니다. 이를 막는 표준 패턴 3가지.

### 3.1. Exponential Backoff

실패 시 대기 시간을 **기하급수적으로** 늘립니다.

| 시도 | 대기 시간 |
| --- | --- |
| 1차 실패 | 1초 |
| 2차 실패 | 2초 |
| 3차 실패 | 4초 |
| n차 실패 | `2^(n-1)` 초 |

> **효과**: 서버가 회복할 물리적 시간을 벌어줍니다.

### 3.2. Jitter (핵심)

Backoff 만 쓰면 모든 클라이언트가 *정확히* 1초, 2초, 4초 뒤에 일제히 요청 → 여전히 spike. 여기에 **무작위성(Randomness)** 을 더하는 것이 **Jitter**.

```java
long wait = (long) Math.pow(2, retryCount) * 1000
          + ThreadLocalRandom.current().nextLong(0, 1000);
```

> **효과**: 뾰족하게 뭉친 요청 그래프를 **넓고 평평하게** 펴줍니다 (Traffic Smoothing).

### 3.3. Circuit Breaker

집의 누전 차단기와 같은 개념.

- 일정 시간 동안 **에러율이 임계치(예: 50%)** 를 넘으면 → **OPEN 상태**.
- OPEN 상태에서는 서버로 요청을 보내지 않고 **즉시 실패(Fail-Fast)**.
- 일정 시간 후 **HALF_OPEN** 으로 전환해 소수 요청만 흘려보내고, 정상이면 **CLOSED** 로 복귀.

> **Spring 실무**: Resilience4j 의 `CircuitBreaker` 또는 Spring Cloud Circuit Breaker 사용.

## 4. Anti-Pattern ②: `throws Exception` (애매한 예외 던지기)

```java
// ❌ Anti-Pattern
public void readFile() throws Exception { ... }
```

### 왜 안 좋은가?

- **모호함**: 호출자는 *"대체 어떤 에러가 날 수 있다는 거야?"* 라고 당황. `IOException` 인지 `SQLException` 인지 알 수 없음.
- **강제 전파(코드 오염)**: 이 메서드를 쓰는 모든 상위 코드가 똑같이 `throws Exception` 을 붙이거나 거대한 `try-catch` 로 감싸야 함.
- **정보 유실**: 네트워크면 재시도, 파일 없으면 생성 같은 **타입별 대응이 불가능**.

### ✅ 권장: 가장 구체적인 예외를 던져라 (Google Java Style)

```java
// ✅ 명확한 방식 - 호출자가 무엇을 대비해야 할지 정확히 알려줌
public void readFile() throws FileNotFoundException, IOException { ... }
```

## 5. 도메인 예외 + 전역 예외 처리 (Spring 실무 패턴)

비즈니스 의미가 있는 예외는 **도메인 전용 예외 클래스** 로 만들고, Controller 가 아닌 **`@RestControllerAdvice`** 에서 일괄 처리하는 것이 정석입니다.

### 5.1. 도메인 예외 정의

```java
public class MemberNotFoundException extends RuntimeException {

    public MemberNotFoundException(final Long memberId) {
        super("Member not found. id=" + memberId);
    }
}
```

> **Tip**: `RuntimeException` 을 상속해 *unchecked* 로 만드는 것이 Spring 생태계의 관례입니다. Checked 로 만들면 service → controller 까지 `throws` 가 따라다녀 코드 오염 발생.

### 5.2. Service 에서 명시적으로 던지기

```java
@Service
@RequiredArgsConstructor
public class MemberService {

    private final MemberRepository memberRepository;

    public Member findById(final Long id) {
        return memberRepository.findById(id)
            .orElseThrow(() -> new MemberNotFoundException(id));
    }
}
```

### 5.3. 전역 예외 처리 (`@RestControllerAdvice`)

```java
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MemberNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(final MemberNotFoundException e) {
        log.warn("Resource not found: {}", e.getMessage());
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(new ErrorResponse("MEMBER_NOT_FOUND", e.getMessage()));
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(final MethodArgumentNotValidException e) {
        return ResponseEntity.badRequest()
            .body(new ErrorResponse("INVALID_REQUEST", e.getMessage()));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleAny(final Exception e) {
        log.error("Unexpected error", e);
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(new ErrorResponse("INTERNAL_ERROR", "예기치 못한 오류가 발생했습니다."));
    }

    public record ErrorResponse(String code, String message) {}
}
```

### 5.4. 왜 이렇게 분리하는가?

1. **Controller 가 얇아진다.** HTTP ↔ Java 변환에만 집중.
2. **응답 포맷이 통일된다.** 모든 에러가 동일한 `ErrorResponse` 구조.
3. **로깅 정책을 한 곳에서 관리.** 4xx 는 warn, 5xx 는 error 등 일관된 정책 적용.

## 6. 절대 잡지 말아야 할 것들

```java
// ❌ Error 를 잡지 말 것
try {
    process();
} catch (OutOfMemoryError e) {
    // 더 큰 문제를 일으킴
}

// ❌ 빈 catch (Exception Swallowing)
try {
    callApi();
} catch (Exception e) {
    // 아무것도 안 함 - 가장 최악
}

// ❌ printStackTrace + continue
try {
    callApi();
} catch (Exception e) {
    e.printStackTrace(); // 로그 시스템에 안 잡힘
}
```

### ✅ 최소한의 catch 규칙

1. **잡았으면 처리하거나, 처리할 수 없으면 던져라** (`throw`).
2. **로그는 `Logger` 를 통해 남겨라** (`printStackTrace` 금지).
3. **원인 예외를 잃지 마라** (`new BusinessException("...", e)` 처럼 cause 를 항상 chaining).

---

## 7. 한 줄 정리

| 상황 | 정공법 |
| --- | --- |
| 재시도 | Exponential Backoff + **Jitter** + Circuit Breaker |
| Exception 시그니처 | **가장 구체적인 예외만** 던지기 (`throws Exception` 금지) |
| 비즈니스 오류 | 도메인 전용 RuntimeException + `@RestControllerAdvice` |
| 시스템 오류 | 잡지 말고 위로 전파 |
| 로그 | Logger 사용, 원인 예외 chaining 필수 |

> **핵심 한 줄**: "예외는 *숨기는* 것이 아니라 *분류해서 책임자에게 전달* 하는 것이다."
