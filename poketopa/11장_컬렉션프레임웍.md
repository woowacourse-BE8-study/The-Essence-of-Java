# 11장. 컬렉션 프레임웍 (Collections Framework)

> `List`, `Set`, `Map` 의 *내부 동작* 을 이해해야 성능 문제를 예방할 수 있습니다.
> "그냥 `ArrayList` 쓰세요" 라는 답을 *왜* 그래야 하는지로 바꿔봅시다.

---

## 1. Collection Framework 전체 구조

```
Iterable
└─ Collection
    ├─ List          (순서 O, 중복 O)
    │   ├─ ArrayList
    │   ├─ LinkedList
    │   └─ Vector (legacy)
    ├─ Set           (순서 X, 중복 X)
    │   ├─ HashSet
    │   ├─ LinkedHashSet
    │   └─ TreeSet
    └─ Queue / Deque (FIFO / 양방향)
        ├─ ArrayDeque
        ├─ LinkedList
        └─ PriorityQueue

Map (Collection 아님, 별도 계층)
    ├─ HashMap
    ├─ LinkedHashMap
    ├─ TreeMap
    └─ Hashtable (legacy)
```

## 2. ArrayList vs LinkedList

### 2.1. 구조적 차이

| 구분 | ArrayList | LinkedList |
| --- | --- | --- |
| **저장 구조** | 메모리의 **연속된 공간** (배열) | **노드(Node)** 가 메모리 여기저기 흩어짐 |
| **다음 원소 접근** | "내 위치 + 1" 로 즉시 계산 | 노드의 `next` 포인터 추적 |
| **비유** | 호텔 복도 (201호 → 202호) | 보물찾기 (쪽지에 다음 위치) |

### 2.2. 성능 비교 (Big-O)

| 연산 | ArrayList | LinkedList |
| --- | --- | --- |
| **조회 `get(i)`** | **O(1)** ✅ | **O(n)** ❌ (head 부터 순회) |
| **끝에 추가/삭제** | **O(1)** ✅ (amortized) | **O(1)** ✅ |
| **중간 삽입/삭제** | **O(n)** ❌ (뒤를 한 칸씩 밀어야 함) | **O(1)** ✅ *(노드 참조를 이미 갖고 있다면)* |
| **메모리 효율** | **좋음** (데이터만 저장) | **나쁨** (`prev`, `next` 포인터 오버헤드) |
| **Cache Locality** | **매우 좋음** ✅ | **나쁨** ❌ |

### 2.3. 자주 오해하는 부분

> **"LinkedList 가 중간 삽입에 빠르다"** 는 말은 *이미 노드 참조가 있을 때* 의 얘기.
> `linkedList.add(5000, value)` 를 호출하면 결국 head 부터 5000번 순회 → **O(n)** 으로 ArrayList 와 동일하거나 더 느립니다.

### 2.4. 실무 결론

> **거의 모든 경우 `ArrayList` 가 정답입니다.**
> 현대 CPU는 **Cache Locality** 가 압도적으로 중요해서 이론적으로 빠를 것 같은 LinkedList 가 실제 벤치마크에선 더 느린 경우가 많습니다.
> `LinkedList` 의 진짜 용처는 **`Deque` 구현체** (양방향 큐) 정도입니다.

## 3. Stack 은 쓰지 마라

### 3.1. `Stack` 클래스의 비극

자바 초창기(JDK 1.0)에 만들어진 `Stack` 은 **`Vector` 를 상속(extends)** 받아 만들어진 클래스입니다.

```java
public class Stack<E> extends Vector<E> { ... }
```

이로 인해 두 가지 치명적 약점을 갖습니다.

#### ① LSP 위반 (Liskov Substitution Principle)

Stack 은 *맨 위* 에서만 넣고 빼야(LIFO) 하는데, `Vector` 를 상속받았기 때문에 `stack.get(0)`, `stack.remove(0)` 처럼 **중간/맨 밑을 마음대로 건드릴 수 있습니다.** *"스택다움"* 이 깨진 것이죠.

#### ② 불필요한 동기화

`Vector` 는 모든 메서드가 `synchronized`. 멀티스레드가 아닐 때도 락 비용을 매번 지불합니다.

### 3.2. 그럼 요즘은 무엇을?

자바 공식 문서에서도 `Stack` 대신 **`Deque`** 사용을 권합니다.

```java
// ✅ 요즘 방식
Deque<Integer> stack = new ArrayDeque<>();
stack.push(1);
stack.push(2);
int top = stack.pop(); // 2
```

| 구현체 | 특징 |
| --- | --- |
| **`ArrayDeque`** | 배열 기반. 거의 항상 최선의 선택 |
| **`LinkedList`** | 노드 기반. `null` 허용이 필요한 드문 경우 |

> **공통점**: 둘 다 `Deque` 인터페이스이므로 *중간에서 데이터 빼기* 같은 비-Stack 적 행위를 막을 수 있습니다.

## 4. 왜 자바는 `Stack`, `Vector` 를 안 고치는가?

### 4.1. "하위 호환성(Backward Compatibility)" 이라는 족쇄

자바의 가장 큰 자랑이자 짐은 **"30년 전 코드가 지금도 컴파일된다"** 는 철학입니다.

- 만약 `Stack` 이 `Vector` 를 상속하지 않게 바꾸면 → 전 세계 금융/국방/의료 시스템의 자바 코드가 컴파일 에러.
- 결론: **"그냥 두고, 더 좋은 새 옷(ArrayList, Deque)을 입으세요"** 로 안내.

### 4.2. 다른 언어는?

| 언어 | 정책 |
| --- | --- |
| **Java** | 절대 안 고침. 새 클래스로 우회 |
| **Python** | Python 2 → 3 에서 *과감히* breaking change. 10년간의 혼란 |
| **Node.js / Swift** | Semantic Versioning + Deprecation 경고로 미리 알리고 Major 에서 삭제 |

> 자바가 욕먹는 그 점(고집)이 자바를 1등으로 유지시키는 이유이기도 합니다. **"어제 짠 코드가 내일도 돌아간다"** 는 신뢰는 기업에게 무엇보다 중요합니다.

## 5. HashMap 의 동작 원리

### 5.1. 저장 단계 (The Hashing Process)

```
put(key, value)
   ↓
key.hashCode()  → int 해시값
   ↓
hash & (capacity - 1)  → bucket 인덱스
   ↓
해당 bucket 에 Node(hash, key, value, next) 저장
```

1. **해시코드 생성**: `key.hashCode()` 호출.
2. **인덱스 계산**: `(n - 1) & hash` 로 내부 배열 인덱스 산출 (n은 2의 제곱수).
3. **데이터 저장**: 해당 bucket 에 `Node` 객체로 저장.

### 5.2. Hash Collision 해결: Chaining → Treeify

서로 다른 key 가 같은 bucket 으로 떨어지는 **해시 충돌** 은 필연적입니다. 자바는 두 방식을 혼용합니다.

```java
static class Node<K, V> {
    final int hash;
    final K key;
    V value;
    Node<K, V> next;   // 👈 chaining 의 핵심
}
```

- **Chaining (Linked List)**: 같은 bucket 에 데이터가 들어오면 `next` 로 줄을 세움.
- **Treeify (Red-Black Tree)**: 한 bucket 의 노드가 **8개 이상** 되면 → Red-Black Tree 로 변환 (검색 O(n) → O(log n)).
- **Untreeify**: 다시 **6개 이하** 가 되면 → Linked List 로 복귀.

### 5.3. `equals` 가 왜 중요한가?

```java
// 같은 bucket 안에서 key 비교
if (e.hash == hash && (e.key == key || (key != null && key.equals(e.key)))) {
    // 같은 key 라고 판단 → value 덮어쓰기
}
```

해시값이 같아도 *실제로* 같은 key 인지 판별하려면 `equals` 가 필요합니다. **그래서 `hashCode` 와 `equals` 는 반드시 함께 재정의해야 합니다.**

> **규약**: `a.equals(b) == true` 이면 `a.hashCode() == b.hashCode()` 도 반드시 참이어야 한다.

### 5.4. Resizing (Rehashing)

#### 기준: Load Factor

```
size > capacity * loadFactor   →   resize
```

- 기본 capacity: **16**
- 기본 loadFactor: **0.75**
- 의미: 16개 bucket 에 데이터가 12개(16 × 0.75)를 넘는 순간 → 배열 크기를 **2배(32)** 로 확장.

#### Rehashing 비용

단순 확장이 아닙니다. **모든 데이터의 bucket 인덱스를 재계산해야 함.**

1. 기존 배열의 2배 크기로 새 배열 생성.
2. 모든 Node 의 인덱스를 `hash & (newCap - 1)` 로 재계산.
3. 새 위치로 모든 데이터 이동.

> **실무 팁**: 저장할 데이터 개수를 알고 있다면 **초기 capacity 를 명시** 해서 resize 비용을 회피.
> ```java
> // 1000개를 저장할 거라면 capacity = 1000 / 0.75 ≈ 1334
> Map<String, User> map = new HashMap<>(1334);
> ```

## 6. HashSet 은 HashMap 의 얇은 wrapper

`HashSet` 의 내부는 사실상 `HashMap` 입니다. value 자리에 **dummy 객체** 를 넣어 key 만 활용.

```java
public class HashSet<E> {
    private transient HashMap<E, Object> map;
    private static final Object PRESENT = new Object();

    public HashSet() {
        map = new HashMap<>();
    }

    public boolean add(E e) {
        return map.put(e, PRESENT) == null;
    }
}
```

> 그래서 `HashSet` 도 `equals` + `hashCode` 의 올바른 구현이 필수입니다.

## 7. Map 의 변형들 (자주 묻는 것)

| 구현체 | 순서 | Null 허용 | thread-safe | 특징 |
| --- | --- | --- | --- | --- |
| **HashMap** | X | key/value 가능 | X | 가장 빠름. 단일 스레드 기본값 |
| **LinkedHashMap** | **입력 순서** 유지 | 가능 | X | LRU 캐시 구현에 활용 |
| **TreeMap** | **key 정렬 순서** | key는 null 불가 | X | Red-Black Tree 기반, O(log n) |
| **Hashtable** | X | 불가 | O | legacy. 쓰지 말 것 |
| **ConcurrentHashMap** | X | key/value 불가 | **O** | 멀티스레드 환경의 정답 |

## 8. 한 줄 정리

| 상황 | 선택 |
| --- | --- |
| 일반 리스트 | **`ArrayList`** |
| Stack (LIFO) | **`ArrayDeque`** (Stack 클래스 X) |
| Queue (FIFO) | **`ArrayDeque`** 또는 `LinkedList` |
| 일반 Map | **`HashMap`** |
| 멀티스레드 Map | **`ConcurrentHashMap`** (Hashtable X) |
| 입력 순서 유지 Map | `LinkedHashMap` |
| 정렬된 Map | `TreeMap` |

> **핵심 한 줄**: "내부 구조를 이해하면 *어떤 자료구조* 가 정답인지는 자동으로 결정된다."
