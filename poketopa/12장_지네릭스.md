# 12장. 지네릭스 (Generics)

> 제네릭은 *컴파일러를 위한 타입 안전 장치* 이지, 런타임 정보가 아닙니다.
> **Type Erasure** 와 **Bounded Wildcard (`extends` / `super`)** 두 개념이 사실상 12장의 전부입니다.

---

## 1. 왜 제네릭을 쓰는가?

### Before (제네릭 없는 시절)

```java
List list = new ArrayList();
list.add("Hello");
list.add(123); // 컴파일러는 모름

String s = (String) list.get(0); // OK
String s2 = (String) list.get(1); // 💥 런타임 ClassCastException
```

### After (제네릭)

```java
List<String> list = new ArrayList<>();
list.add("Hello");
list.add(123); // ❌ 컴파일 에러
```

> **핵심**: 런타임에 터질 `ClassCastException` 을 **컴파일 타임에 잡아주는 것**. 그게 제네릭의 목적입니다.

---

## 2. Type Erasure (타입 소거) — 자바 제네릭의 진실

### 2.1. 우리가 작성한 코드 (Before Compile)

```java
public class Box<T> {
    private T item;

    public void set(T item) { this.item = item; }
    public T get() { return item; }
}

Box<String> box = new Box<>();
box.set("Hello");
String str = box.get();
```

### 2.2. 컴파일 후 (Runtime)

```java
public class Box {              // <T> 가 사라짐
    private Object item;        // T → Object

    public void set(Object item) { this.item = item; }
    public Object get() { return item; }
}

Box box = new Box();
box.set("Hello");
String str = (String) box.get(); // 컴파일러가 형변환 자동 삽입
```

### 2.3. 그래서 무엇이 문제인가?

런타임에는 `List<String>` 과 `List<Integer>` 의 **정체가 똑같습니다.**

```java
List<String>  sList = new ArrayList<>();
List<Integer> iList = new ArrayList<>();

System.out.println(sList.getClass() == iList.getClass());
// 결과: true (둘 다 그냥 ArrayList.class)
```

### 2.4. 왜 이렇게 만들었나?

자바 1.4 까지는 제네릭이 없었습니다. 1.5 에서 제네릭을 도입할 때 **"옛날 코드와 새 코드가 섞여 돌아가게"** 하려고 타입을 지워버리는 방식을 택했습니다. → **하위 호환성(Backward Compatibility)**.

### 2.5. Type Erasure 의 부작용 (면접 단골)

```java
// ❌ 1. 제네릭 타입으로 instanceof 불가
if (obj instanceof List<String>) { } // 컴파일 에러

// ❌ 2. 제네릭 배열 생성 불가
T[] arr = new T[10]; // 컴파일 에러

// ❌ 3. static 컨텍스트에서 타입 파라미터 사용 불가
public class Box<T> {
    private static T staticItem; // 컴파일 에러
}

// ❌ 4. 같은 타입 파라미터 다른 구체 타입으로 오버로딩 불가
void foo(List<String> l) { }
void foo(List<Integer> l) { } // 컴파일 에러: erasure 후 시그니처 동일
```

## 3. Wildcard: `<? extends T>` vs `<? super T>`

가장 헷갈리는 부분. **PECS** 원칙으로 외우면 절대 안 잊습니다.

> ### 🌟 PECS: **P**roducer **E**xtends, **C**onsumer **S**uper

### 3.1. `<? extends T>` — Producer (꺼내기 전용)

> **"꺼내서 먹기만 할 거야"** 라고 기억하세요.

```java
public double sumOfFruits(List<? extends Fruit> fruits) {
    double total = 0;
    for (Fruit f : fruits) {  // ✅ 읽기: Fruit 으로 받을 수 있음
        total += f.getWeight();
    }
    // fruits.add(new Apple()); // ❌ 컴파일 에러
    return total;
}
```

- **상황**: 과일 바구니에서 꺼내서 `eat()` 호출.
- **보장**: 사과든 포도든 **결국 다 Fruit** 인 것은 확실 → 읽기 OK.
- **금지**: 여기에 `Apple` 을 *새로* 넣을 수는 없음. 실제로 `List<Grape>` 일 수도 있으니까. → 쓰기 NO.

> **핵심**: 꺼낸 놈의 **최소 신분(T)** 을 보장받고 싶을 때.

### 3.2. `<? super T>` — Consumer (담기 전용)

> **"여기에 담기만 할 거야"** 라고 기억하세요.

```java
public void addApples(List<? super Apple> basket) {
    basket.add(new Apple());      // ✅ 쓰기: Apple 은 무조건 들어감
    basket.add(new Fuji());       // ✅ Apple 의 자식도 OK
    // Apple a = basket.get(0);   // ❌ 컴파일 에러
    Object o = basket.get(0);     // 읽기는 Object 로만
}
```

- **상황**: 사과(`Apple`)를 바구니에 담음.
- **보장**: 이 바구니는 `List<Apple>`, `List<Fruit>`, `List<Object>` 중 하나 → Apple 을 담는 것은 항상 안전.
- **불편**: 꺼낼 때는 `Apple` 인지 그냥 `Object` 인지 알 수 없음 → 읽기는 `Object` 로만 가능.

> **핵심**: 내가 가진 놈을 **어디든 안전하게 담고 싶을 때**.

### 3.3. 한눈에 비교

| 구분 | `<? extends T>` (상한) | `<? super T>` (하한) |
| --- | --- | --- |
| **별명** | **Producer (생산자)** | **Consumer (소비자)** |
| **주 용도** | 데이터를 **꺼낼 때** | 데이터를 **넣을 때** |
| **읽기 (get)** | ✅ `T` 타입으로 안전하게 읽음 | ⚠️ `Object` 로만 읽힘 |
| **쓰기 (add)** | ❌ 불가능 (`null` 만 가능) | ✅ `T` 와 그 자식 |
| **암기** | **P**roducer **E**xtends | **C**onsumer **S**uper |

## 4. 왜 이렇게 복잡하게 만들었나? — Type Safety 의 본질

만약 `List<? extends Fruit>` 에 사과를 넣는 게 허용된다고 가정해봅시다.

```java
List<Grape>           grapes = new ArrayList<>();
List<? extends Fruit> fruits = grapes;   // 합법 (공변성)
fruits.add(new Apple());                  // 만약 허용된다면...
Grape g = grapes.get(0);                  // 💥 ClassCastException
```

알고 보니 그 리스트가 *포도 리스트* 였다면, 나중에 포도를 꺼낼 줄 알았던 다른 코드에서 사과가 튀어나와 프로그램이 터집니다.

> 자바 컴파일러는 이런 **'끔찍한 혼종'** 이 생기는 것을 막기 위해 읽기/쓰기 권한을 엄격히 제한합니다.

## 5. JDK 표준 라이브러리의 PECS 적용 예시

`Collections.copy` 시그니처를 보면 PECS 가 그대로 적용되어 있습니다.

```java
public static <T> void copy(
    List<? super T>   dest,   // dest 에는 '넣기' 만 함 → Consumer Super
    List<? extends T> src     // src 에서는 '꺼내기' 만 함 → Producer Extends
) {
    for (int i = 0; i < src.size(); i++) {
        dest.set(i, src.get(i));
    }
}
```

`Stream.collect(Collector<? super T, A, R>)` 도 마찬가지.

## 6. 제네릭 메서드 패턴 (실무에서 자주 쓰는 형태)

```java
public class GenericUtils {

    // ✅ Producer Extends
    public static <T> List<T> copyOf(Collection<? extends T> source) {
        return new ArrayList<>(source);
    }

    // ✅ Consumer Super
    public static <T> void addAll(Collection<? super T> dest, T... items) {
        for (T item : items) {
            dest.add(item);
        }
    }

    // ✅ 다중 타입 파라미터
    public static <K, V> Map<V, K> invert(Map<K, V> map) {
        return map.entrySet().stream()
            .collect(Collectors.toMap(Map.Entry::getValue, Map.Entry::getKey));
    }
}
```

## 7. 실무 예시 (예: 장기 게임 프로젝트)

```java
public class Board {

    // Piece 의 자식 모두를 꺼내 화면에 그릴 때 → Producer
    public void render(List<? extends Piece> pieces) {
        pieces.forEach(this::drawPiece);
    }

    // Piece 를 어떤 컨테이너든 안전하게 담을 때 → Consumer
    public void place(List<? super Piece> destination, Piece piece) {
        destination.add(piece);
    }
}
```

## 8. 한 줄 정리

| 키워드 | 의미 | 암기 |
| --- | --- | --- |
| **Type Erasure** | 컴파일 후 제네릭 타입이 사라짐 | "런타임에는 `List<T>` 는 그냥 `List`" |
| **`<? extends T>`** | T 또는 T의 자식 (읽기 OK, 쓰기 X) | **Producer** Extends |
| **`<? super T>`** | T 또는 T의 부모 (쓰기 OK, 읽기 Object) | **Consumer** Super |
| **PECS** | API 설계의 황금률 | **P**roducer **E**xtends, **C**onsumer **S**uper |

> **핵심 한 줄**: "`extends` = **나오는 놈의 신분 보장**, `super` = **들어가는 놈의 안전 입주**."
