# 7장. 내부 클래스 (Inner Class)

> 자바의 정석 7장 중 **내부 클래스** 파트를 정리합니다. 단순 문법보다 *왜 위험한지*, *왜 그럼에도 쓰는지*에 초점을 맞춥니다.

---

## 1. 내부 클래스의 4가지 종류

| 종류 | 선언 위치 | static 여부 | 특징 |
| --- | --- | --- | --- |
| **Static Nested Class** | 클래스 멤버 | `static` O | 외부 인스턴스와 독립 |
| **Inner Class (멤버)** | 클래스 멤버 | `static` X | 외부 인스턴스 참조 보유 |
| **Local Inner Class** | 메서드 내부 | - | 메서드 스코프에 한정 |
| **Anonymous Class** | 표현식 내부 | - | 이름 없는 일회용 클래스 |

> 자바 공식 문서에서도 `static`이 붙은 클래스는 **'Inner Class(내부 클래스)'** 라고 부르지 않고, **'Static Nested Class(정적 중첩 클래스)'** 로 따로 분류합니다. 성격상 *"이름만 빌려 쓰는 외부 클래스"* 에 훨씬 가깝기 때문입니다.

---

## 2. 비정적(non-static) 내부 클래스가 위험한 이유

### 2.1. 숨은 참조 (Hidden Reference) 와 메모리 누수

`static`이 없는 내부 클래스는 자신을 감싸고 있는 외부 클래스에 대한 **숨은 참조**를 가집니다. 컴파일러가 내부적으로 `this$0` 라는 필드를 만들어 외부 인스턴스를 붙들고 있기 때문입니다.

```java
public class LargeActivity {
    private byte[] hugeData = new byte[100 * 1024 * 1024]; // 100MB

    // ⚠️ static 이 없으므로 LargeActivity 의 참조를 들고 있음
    private class HeavyTask implements Runnable {
        @Override
        public void run() {
            sleep(10_000); // 10초 동안 점유
        }
    }

    public void start() {
        new Thread(new HeavyTask()).start();
    }
}
```

#### 무엇이 문제인가?

1. 사용자가 `LargeActivity`를 열었다가 바로 닫음 → GC 대상이 되어야 함.
2. 하지만 `HeavyTask`는 10초 동안 실행 중.
3. `HeavyTask`는 `static`이 아니므로 `LargeActivity`의 인스턴스를 잡고 있음.
4. **결과적으로 이미 닫힌 100MB짜리 `LargeActivity`가 GC 되지 못하고 메모리에 남음.** → **Memory Leak**

### 2.2. 그 외 단점 (Anti-Pattern 신호)

- **테스트의 어려움**: 외부 클래스 인스턴스 없이 단독으로 unit test 하기 어려움.
- **클래스 비대화**: 내부 클래스가 많아지면 SRP (Single Responsibility Principle) 위반 신호.
- **직렬화(Serialization) 호환성**: 내부 클래스의 직렬화 형태는 표준이 아니어서 JVM/버전 간 호환 깨질 위험.

---

## 3. 그래서 결론: `static` 을 붙여라

### 3.1. 메모리 관점에서 본 차이

- **일반 Inner Class**: 외부 객체와 *밧줄(참조)* 로 묶여 생사고락을 함께함.
- **Static Nested Class**: 외부 클래스와 **완전히 독립된 덩어리**. 외부 인스턴스가 0개든 100개든 무관.

```java
public class Outer {
    // ✅ 권장: 외부 인스턴스에 의존하지 않는 보조 클래스
    static class CpuStatus {
        int usage;
        int temperature;
    }
}
```

### 3.2. 그렇다면 왜 굳이 "안에" 넣는가? (빅테크의 관점)

외부 파일로 빼지 않고 안에 두는 이유는 **논리적 그룹화** 와 **가시성 제어** 때문입니다.

#### ① 논리적 그룹화 (Cohesion)
`Computer` 클래스에서만 의미 있는 `CpuStatus` 라면, 별도 파일보다 `Computer.CpuStatus`로 두는 게 *"이 클래스는 오직 Computer를 돕기 위해 존재한다"* 는 의도를 코드로 드러냅니다.

#### ② 캡슐화 (Encapsulation)
외부 파일은 최소 `default` (package-private) 노출이 강제됩니다. 하지만 정적 중첩 클래스는 **`private static class`** 로 선언할 수 있어, 외부 클래스 외에는 존재 자체를 모르게 숨길 수 있습니다.

#### ③ 패키지 정리
거대한 프로젝트에서 사소한 보조 클래스를 모두 파일로 만들면 패키지 트리가 폭발합니다. 관련 있는 것끼리 묶어두면 유지보수성이 올라갑니다.

### 3.3. 정적 중첩 클래스의 유일한 "특권"

외부 클래스의 **`private` 멤버에 접근 가능합니다.** 일반 외부 클래스는 다른 클래스의 `private`을 절대 볼 수 없지만, 정적 중첩 클래스는 자신을 감싸고 있는 외부 클래스의 `private` 멤버를 내 것처럼 가져다 쓸 수 있습니다. *일종의 '가족 특권'*.

## 4. 익명 클래스 (Anonymous Class) 도 비정적 내부 클래스다

```java
public class Service {
    public void register() {
        // 익명 클래스는 사실상 non-static inner class
        Runnable task = new Runnable() {
            @Override
            public void run() {
                System.out.println("hi");
            }
        };
        new Thread(task).start();
    }
}
```

### 빅테크 면접 단골 질문

> ⚠️ **위험성**
> 익명 클래스가 외부 클래스의 인스턴스 메서드 안에서 생성되면, 외부 클래스에 대한 **숨은 참조**를 가집니다.
> 이 익명 객체가 별도의 thread / executor 에서 오래 살아있다면, 외부 클래스가 GC 되지 못해 **Memory Leak** 발생.

### 람다는 다르다 (중요)

자바 8 이상의 **람다 표현식**은 **익명 클래스의 단순 치환이 아닙니다.**

- 익명 클래스: `OuterClass$1.class` 같은 별도 `.class` 파일이 생성되고, 항상 외부 인스턴스 참조를 가질 가능성이 있음.
- 람다: `invokedynamic` + `LambdaMetafactory` 기반. 외부 멤버를 캡처하지 않는 한 외부 인스턴스 참조를 만들지 않음.

```java
// 👍 권장: this$0 캡처를 방지
Runnable safe = () -> System.out.println("no hidden reference");

// ⚠️ 외부 인스턴스 멤버를 캡처하면 동일하게 누수 위험
Runnable risky = () -> System.out.println(this.hugeData.length);
```

## 5. 메모리 누수를 막는 실무 패턴

### 5.1. `static` + 외부 데이터 명시 전달

```java
public class LargeActivity {
    private byte[] hugeData;

    // ✅ static 으로 선언하고, 필요한 데이터만 명시적으로 주입
    private static class HeavyTask implements Runnable {
        private final WeakReference<LargeActivity> ownerRef;

        HeavyTask(LargeActivity owner) {
            this.ownerRef = new WeakReference<>(owner);
        }

        @Override
        public void run() {
            LargeActivity owner = ownerRef.get();
            if (owner == null) return; // 이미 GC 되었으면 작업 중단
            // ... do something with owner ...
        }
    }
}
```

### 5.2. WeakReference 패턴의 핵심

- `WeakReference` 는 GC 가 자유롭게 회수할 수 있는 약한 참조.
- 외부 객체가 더 이상 강한 참조에서 살아있지 않다면, `ref.get()` 은 `null` 을 반환.
- → 외부 객체의 수명을 **연장하지 않으면서도** 필요할 때 접근 가능.

---

## 6. 한 줄 정리

| 상황 | 권장 |
| --- | --- |
| 외부 인스턴스 상태가 필요 없음 | **`static` nested class** |
| 외부 인스턴스 상태가 꼭 필요함 | non-static inner class + **수명 동일성 보장** |
| 일회성 콜백/리스너 | **lambda** (가능하면 외부 캡처 금지) |
| 백그라운드 thread / Executor | **반드시 `static` + 명시 주입 + 가능하면 `WeakReference`** |

> **핵심 한 줄**: "내부 클래스를 쓸 때는 일단 `static` 을 붙여라. 못 붙이는 이유가 있을 때만 떼라."
