# 13장. 쓰레드와 동기화 (Thread & Synchronization)

> "어? 단일 스레드에서는 잘 됐는데..." 라는 말의 90%는 **동기화** 를 잘못 이해해서 나옵니다.
> Legacy 동기화 컬렉션의 함정과 modern `java.util.concurrent` 의 대안을 정리합니다.

---

## 1. Thread-safety 란 무엇인가?

> 여러 스레드가 동시에 접근해도 **데이터의 일관성** 이 깨지지 않는 것.

깨지는 대표적 원인은 세 가지.

| 문제 | 설명 |
| --- | --- |
| **Race Condition** | 두 스레드의 연산 순서에 따라 결과가 달라짐 |
| **Visibility** | 한 스레드의 변경이 다른 스레드에게 안 보임 (CPU 캐시 / JIT 최적화) |
| **Atomicity** | `i++` 같은 *한 줄짜리 연산* 도 실제로는 read-modify-write 3단계 |

## 2. Legacy 동기화 컬렉션 (Vector, Hashtable, Stack)

### 2.1. 무엇이 다른가?

자바 초기 버전(JDK 1.0)부터 존재했던 클래스들로, **거의 모든 메서드에 `synchronized`** 가 붙어 있어 thread-safe 합니다.

| 클래스 | 현대적 대체재 | 특징 |
| --- | --- | --- |
| **`Vector`** | `ArrayList` + `Collections.synchronizedList` / `CopyOnWriteArrayList` | 모든 메서드 `synchronized` |
| **`Hashtable`** | `ConcurrentHashMap` | `null` key/value 불가 |
| **`Stack`** | `ArrayDeque` (단일) / `ConcurrentLinkedDeque` (멀티) | `Vector` 상속의 비극 |

### 2.2. 왜 요즘은 안 쓰나?

#### 문제 ①: 과도한 락(Lock) → 성능 저하

`Vector` 는 모든 메서드에 `synchronized`. 문제는 **읽기 전용 작업(`get`, `size`)** 도 무조건 락을 건다는 점입니다.

- **단일 스레드**: 혼자 쓰는데도 매번 락을 걸고 푸는 비용 → `ArrayList` 보다 항상 무거움.
- **멀티 스레드**: 여러 스레드가 동시에 `get()` 을 호출해도 한 명이 락을 잡으면 나머지는 줄을 섬. 읽기가 대부분인 워크로드에서 치명적인 **bottleneck**.

#### 문제 ②: "완벽하지 않은" Thread-Safety (The Illusion of Thread-safety)

**개별 메서드가 동기화되어 있다고, 그 메서드들을 조합한 작업까지 안전한 것은 아닙니다.**

```java
// ⚠️ 함정: 각 메서드는 synchronized 인데 조합은 안전하지 않음
int lastIndex = vector.size() - 1;  // (1) synchronized
vector.remove(lastIndex);           // (2) synchronized

// (1) 과 (2) 사이의 찰나에 다른 스레드가 마지막 요소를 삭제하면
// (2) 에서 ArrayIndexOutOfBoundsException 💥
```

결국 안전하게 만들려면 **외부에서 다시 `synchronized` 블록으로 감싸야** 합니다.

```java
synchronized (vector) {
    int lastIndex = vector.size() - 1;
    vector.remove(lastIndex);
}
```

> **결론**: 어차피 외부에서 락을 걸어야 한다면, 내부에서 무겁게 락을 들고 있는 `Vector` 를 쓸 이유가 사라집니다.

## 3. 현대적 동기화 컬렉션 (`java.util.concurrent`)

### 3.1. `ConcurrentHashMap`

`Hashtable` 의 후계자. **세그먼트 락(Java 7) → CAS + synchronized bucket (Java 8+)** 으로 진화하며 read-heavy 워크로드에서 압도적인 성능.

```java
ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();

// ✅ atomic 한 read-modify-write
map.compute("counter", (k, v) -> v == null ? 1 : v + 1);
map.computeIfAbsent("user", k -> loadFromDB(k));
map.merge("hit", 1, Integer::sum);
```

> ⚠️ 주의: `null` key 와 `null` value 모두 **불가능**. 멀티스레드 환경에서 `null` 의 모호함이 너무 위험하기 때문.

### 3.2. `CopyOnWriteArrayList`

**쓰기 시점에 배열을 복사** 해서 새 배열을 만드는 방식. 읽기는 락 없이 진행.

```java
List<Listener> listeners = new CopyOnWriteArrayList<>();
listeners.forEach(Listener::onEvent); // 락 없이 안전
```

- **장점**: 읽기 락이 없어 매우 빠름. iterator 가 `ConcurrentModificationException` 없이 안전.
- **단점**: 쓰기마다 배열 복사 → 쓰기가 많으면 **메모리/성능 폭탄**.
- **용도**: **읽기는 매우 많고, 쓰기는 거의 없는** 케이스 (이벤트 리스너, 옵저버 등).

### 3.3. 기타 유용한 도구들

| 도구 | 용도 |
| --- | --- |
| `AtomicInteger`, `AtomicLong` | CAS 기반의 lock-free 카운터 |
| `LongAdder` | 고경합 환경의 카운터 (`AtomicLong` 보다 빠름) |
| `ConcurrentLinkedQueue` | lock-free FIFO 큐 |
| `BlockingQueue` (`LinkedBlockingQueue` 등) | Producer-Consumer 패턴 |
| `ReentrantLock`, `ReadWriteLock` | `synchronized` 보다 세밀한 락 제어 |

## 4. `synchronized` vs `ReentrantLock`

| 구분 | `synchronized` | `ReentrantLock` |
| --- | --- | --- |
| **사용 편의** | ✅ 키워드 하나로 끝 | ❌ `try-finally` 로 `unlock` 명시 필요 |
| **JVM 모니터링** | ✅ thread dump 에 잘 나옴 | △ |
| **타임아웃 락** | ❌ | ✅ `tryLock(time, unit)` |
| **인터럽트 가능 락** | ❌ | ✅ `lockInterruptibly()` |
| **공정성(fair) 옵션** | ❌ | ✅ |
| **조건 변수** | ❌ (`wait/notify` 만) | ✅ 여러 `Condition` |

```java
private final ReentrantLock lock = new ReentrantLock();

public void doWork() {
    lock.lock();
    try {
        // critical section
    } finally {
        lock.unlock(); // ✅ 반드시 finally 에서 해제
    }
}
```

> **권장**: 단순 동기화는 `synchronized`, 세밀한 제어가 필요하면 `ReentrantLock`.

## 5. 동기화의 정공법 — 가능하면 *공유하지 마라*

빅테크 코드베이스의 동기화 원칙은 의외로 단순합니다.

1. **Immutable Object**: 변하지 않으면 동기화가 필요 없음 (`record`, `final` 필드).
2. **Thread-Local 데이터**: 각 스레드가 자기 데이터만 만지면 충돌 자체가 없음 (`ThreadLocal`).
3. **공유가 정말 필요할 때만** `java.util.concurrent` 의 검증된 자료구조 사용.
4. **`synchronized` / `Lock` 은 최후의 수단.**

```java
// ✅ Immutable: 동기화 자체가 필요 없음
public record Money(long amount, Currency currency) {
    public Money add(Money other) {
        return new Money(amount + other.amount, currency); // 새 객체 반환
    }
}
```

## 6. Spring 환경에서 자주 보는 함정

### 6.1. `@Service` 는 기본적으로 Singleton 이다

```java
@Service
public class CounterService {
    private int count = 0; // ⚠️ 모든 요청이 공유하는 상태

    public void increase() {
        count++; // ❌ race condition
    }
}
```

> Spring Bean 은 기본 scope 가 `singleton` → 인스턴스 필드는 *모든 요청 스레드가 공유* 합니다.
> Service 계층에서는 **stateless** 를 원칙으로 하세요.

### 6.2. `@Transactional` 안에서 `synchronized` 의 함정

```java
@Service
public class WrongService {
    @Transactional
    public synchronized void register(Order order) { // ❌
        // 트랜잭션 commit 이 unlock 보다 먼저 발생 X
        // → 다른 스레드가 락을 잡아도 commit 되지 않은 상태를 못 봄
    }
}
```

분산 환경에서는 어차피 JVM 단의 락은 무의미. **DB 의 비관/낙관적 락 또는 분산 락 (Redis Redisson 등)** 을 사용해야 합니다.

## 7. 한 줄 정리

| 상황 | 정답 |
| --- | --- |
| 단일 스레드 List | `ArrayList` |
| 멀티 스레드 List (읽기 多) | `CopyOnWriteArrayList` |
| 단일 스레드 Map | `HashMap` |
| 멀티 스레드 Map | **`ConcurrentHashMap`** (Hashtable X) |
| 단순 카운터 | `AtomicLong` 또는 `LongAdder` |
| 단순 임계영역 보호 | `synchronized` |
| 타임아웃/인터럽트 락 필요 | `ReentrantLock` |
| Producer-Consumer | `BlockingQueue` |

> **핵심 한 줄**: "동기화의 정답은 *동기화를 줄이는 것* 이다. Immutable → ThreadLocal → j.u.c → synchronized 순으로 고려하라."
